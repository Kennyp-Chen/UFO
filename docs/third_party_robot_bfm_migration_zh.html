第三方机器人迁移到 UFO 进行 BFM 训练

准备清单、接口契约、数据门禁和分阶段验收。本文面向已经拥有机器人描述文件与专家轨迹、需要接入 UFO 的工程人员。

目标边界 机器人资产 专家轨迹 配置契约 运行环境 验收门禁

1. 先确定迁移边界

UFO 的第三方机器人入口由三部分组成：一份可由 MuJoCo/MJLab 加载的 MJCF、一份机器人 YAML，以及已经 retarget 到该机器人关节空间的专家轨迹。算法仍使用 UFO 的 FB 或 TeCH；迁移工作的重点是保证物理模型、策略动作和轨迹 DOF 三者完全对齐。

不在迁移范围内：UFO 不负责把人体动作或其他机器人动作自动 retarget 到目标机器人；G1 checkpoint 也不能直接用于新机器人的继续训练或推理。
对象唯一事实来源必须一致的下游项
动力学与拓扑训练专用 MJCFbody、joint、qpos/qvel 地址、碰撞、惯量
策略动作布局机器人 YAML 的 control_joints动作维度、默认姿态、PD、力矩/速度限制
专家动作布局轨迹中的 joint_names 和 dof列数、列顺序、单位、采样率

2. 机器人描述文件准备

2.1 必需文件

  • MJCF/XML：训练与推理的物理模型，必须有浮动基座和每个可控单自由度关节。
  • mesh/texture：MJCF 引用的所有资源，路径在迁移后仍可解析；建议采用相对路径。
  • URDF（推荐）：用于核对 effort、velocity、damping、friction 和左右关节语义，但不取代 MJCF 的 qpos/qvel 布局。
  • 资产版本记录：型号、发布日期或提交号，防止描述文件与轨迹来自不同硬件版本。

2.2 MJLab 兼容要求

  • 根 body 应使用 <freejoint name="..."/>；避免写成 <joint type="free">，后者会被当前 MotionLib 误计为一个 actuator body。四元数约定必须写入机器人 YAML。
  • 每个控制关节应为 hinge/slide 单自由度关节，名称全局唯一。
  • UFO 当前 MJLab 构建器会在 Python 侧创建 DC motor。训练 MJCF 不应在 joint 上保留 actuatorfrcrange，已有 XML actuator 会在建模时被替换。
  • MotionLib 仍需要 MJCF 中存在显式 <actuator>，建议为每个策略关节添加同名 motor；这同时让导入检查能够确定动作顺序。
  • 碰撞几何必须覆盖双脚，并避免仅有 visual mesh 而无有效 collision geom。
保留供应商原始 XML，另生成训练专用 XML。不要在无法追溯的情况下直接覆盖原始模型。

2.3 初步检查

uv run python -m humanoidverse.tools.robot_inspect \
  --xml /path/to/robot_training.xml \
  --urdf /path/to/robot.urdf \
  --name my_robot \
  --out /tmp/my_robot_draft.yaml \
  --hydra-out humanoidverse/config/robot/my_robot/my_robot_auto.yaml

生成结果只是草稿。工具能推断结构，却无法可靠决定足端、手端、躯干、接触惩罚、默认站姿和控制器参数。

3. 专家轨迹准备

训练推荐使用接近 10 秒的 clip，推理与跟踪评估保留完整序列。大数据不应提交到 Git，可由 manifest 读取共享磁盘路径或环境变量展开后的路径。

字段要求常见错误
root_trans_offset[T, 3]，米，z-up毫米未换算、根高度重复叠加
root_rot[T, 4]，确认 xyzw/wxyz顺序错误导致模型侧躺
dof / dof_pos[T, N]，弧度，N 等于策略动作数按字母排序而非控制顺序
pose_aa[T, body_count, 3]包含 world body 或缺少固定 body
fps正数且与真实采样率一致重采样后仍保留旧 fps
joint_names与 control_joints逐项相同左右腿或头/手顺序不同

3.1 推荐的数据组织

/shared/ufo-data/my_robot/
├── my_robot_full.pkl
├── my_robot_10s-clipped.pkl
└── SHA256SUMS

训练与推理分开引用，避免用裁剪数据做长序列评估。迁移前记录 motion 数量、总帧数、fps 分布、关键 tensor shape 和 SHA-256。

4. UFO 配置契约

4.1 机器人 YAML

configs/robots/<robot>.yaml 至少需要：

  • xml_path、base_body、四元数和坐标系约定；
  • 显式或 actuator 推导的 control_joints；
  • feet、hands、key_bodies；
  • training.hydra_robot 和语义 body/ankle 配置；
  • 完整默认姿态、PD gains、action scale；
  • 与关节顺序等长的 effort/velocity limits；
  • 每关节 actuator 的 effort、velocity、armature、friction。

4.2 Hydra 机器人配置

humanoidverse/config/robot/<robot>/<variant>.yaml 提供算法环境仍需的机器人分组、左右对称信息、随机化 body 集合及 motion 语义。运行时会由 robot training spec 覆盖动作维度、body 列表、限位和控制参数。

4.3 数据 manifest

robot_config: configs/robots/my_robot.yaml
datasets:
  - name: my_robot_expert
    format: ufo_pkl
    train_path: ${oc.env:MY_ROBOT_MOTION_DIR}/my_robot_10s-clipped.pkl
    inference_path: ${oc.env:MY_ROBOT_MOTION_DIR}/my_robot_full.pkl
    weight: 1.0
可移植性要求：服务器上只需重新设置数据根目录，不应修改并提交 manifest 中的机器私有绝对路径。

5. 软件与硬件准备

  • Linux、Python 3.10、支持项目锁定依赖的 uv。
  • NVIDIA 驱动与项目 PyTorch/CUDA 组合兼容；多卡节点可正常执行 NCCL all-reduce。
  • 每张 GPU 有独立仿真环境和 replay buffer；--num-envs 与 --buffer-size 均是每 rank 数值。
  • 共享存储应能承受 8 个进程并发读专家轨迹；必要时训练前复制到节点本地 NVMe。
  • 运行目录、缓存目录和 W&B 目录预留足够空间，并与源码目录分开。

6. 分阶段验收门禁

  1. 资产门禁：MuJoCo 可加载 MJCF；mesh 无缺失；nq/nv/body/joint 数符合预期。
  2. 布局门禁：控制关节、MJCF actuator、轨迹 joint_names 三者逐项一致。
  3. 轨迹门禁：所有 motion shape、fps、有限值、四元数范数与关节限位检查通过。
  4. 配置门禁：load_robot_training_spec 成功，默认姿态完整，所有语义名称存在。
  5. 单环境门禁：构建环境后静止若干步，无 NaN、爆炸力矩或穿地。
  6. 单卡 smoke：16 个环境、2048 global steps，能够采样、更新并写 checkpoint。
  7. 单卡短训：观察 reward、episode length、buffer 和显存曲线，排除系统性异常。
  8. 多卡 smoke：8 rank 初始化、step 同步、checkpoint 和退出均正常。
  9. 正式训练：固定资产/数据 hash、配置、seed、依赖锁和启动命令。

完成机器人 YAML 和数据 manifest 后，用强校验工具一次执行资产、布局、shape、有限值、四元数和数据哈希门禁：

uv run python -m humanoidverse.tools.validate_bfm_setup \
  --robot-config configs/robots/my_robot.yaml \
  --data-manifest configs/data/my_robot_motion.yaml
停止条件：出现 NaN、关节顺序不一致、根姿态明显错误、持续触地穿透、显存持续增长、不同 rank step 分叉时，不应直接扩大环境数继续训练。
