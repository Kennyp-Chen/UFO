PiPlus Soccer × BFM：足球状态扩展与训练实施方案

面向 PiPlus_S_12L8A0G2H0W 的对象条件 BFM 训练设计。本文记录已经确认的仓库事实、足球轨迹契约、无球能力保留方案、阶段门禁及后续会话接手信息。

方案结论 当前基线 足球源任务 状态定义 轨迹契约 无球兼容 框架改造 实施阶段 验收指标 决策风险 会话接手

1. 方案结论

目标是把足球作为一个外部刚体加入 BFM 的状态，而策略动作仍然是 PiPlus 的关节目标。训练状态从纯机器人状态 s_robot 扩展为：

s_t = [ robot_state_t, ball_state_t, command_t, object_active_t ] a_t = robot_joint_action_t s_(t+1) = simulator_step(s_t, a_t)

在这个定义下，策略可以学习“当前机器人—足球联合状态经过动作后如何转移”，并用包含足球目标的状态切片或目标条件来查询动作。这个方向是可行的，但不能只在 pkl 末尾机械追加 6 个数：环境、观测编码器、专家 buffer、目标状态、评估和渲染必须共享同一对象状态契约。

推荐路线：以已经接入 UFO 的 H0W 为唯一足球主型号；使用现有 piplus_soccer 策略和采集器生成同步机器人—足球轨迹；先做纯盘带，再做踢球，最后混合。原有 LaFAN 轨迹通过 object_active=0 保留，而不是用一个未标记的“假球”污染状态转移。
当前边界：截至 2026-07-24，UFO 仓库中只完成了 H0W 无球模型、动作数据、smoke 和轨迹 MP4 渲染。足球刚体、足球观测和足球训练尚未接入。

1.1 对最初两个想法的判断

想法判断工程化修正
用带球/踢球策略生成机器人和足球联合轨迹，让 BFM 学会对象条件状态转移 可行，且是主路线 必须保证球状态、机器人状态、action 和 command 同帧；BFM 状态编码和目标条件需要显式增加对象分支；物理转移仍由在线模拟器产生，专家轨迹提供覆盖与先验。
给旧 pkl 手动加入一个放在远处的固定足球，保持本体运动能力 有条件可用 必须增加 object_active/ball_valid mask 并屏蔽足球相关损失。若没有 mask，模型会把“足球永远冻结在远处”学成真实动力学，且固定在机器人坐标系会违反物理一致性。

4. BFM 足球状态定义

4.1 原始可回放状态（数据层）

数据层应保留能够完整回放和检查物理一致性的状态。推荐最小集合：

分组字段shape说明
机器人root_trans_offset[T,3]米，z-up，环境局部 world frame
机器人root_rot[T,4]UFO 统一使用 xyzw
机器人dof / dof_pos[T,22]H0W control-joint 顺序，弧度
机器人pose_aa[T,27,3]与 H0W 非 world body 顺序一致
足球ball_pos_w[T,3]球心世界位置，米
足球ball_quat_w[T,4]用于完整回放；必须记录四元数顺序元数据
足球ball_lin_vel_w[T,3]m/s
足球ball_ang_vel_w[T,3]rad/s，旋转/摩擦研究需要
任务command[T,7]保留源任务 command，mode 必须取 0/1/2
接触foot_ball_contact[T,2]左/右足布尔接触
接触foot_ball_contact_force[T,2]接触力标量或约定后的 norm
兼容object_active[T,1]真实足球轨迹为 1，无球兼容轨迹为 0

4.2 策略/表示学习状态（模型层）

策略不应直接依赖绝对 world xy。推荐将足球状态转为机器人 yaw 对齐坐标系，减少平移和航向变化：

ball_features = [
  ball_pos_yaw_frame_xyz,       # 3
  ball_lin_vel_yaw_frame_xyz,   # 3
  ball_ang_vel_yaw_frame_xyz,   # 3，可在第一版消融
  left_right_contact,           # 2
  object_active                 # 1
]

command_features = [
  target_vel_xy,                # 2
  target_ball_pos_xy,           # 2
  mode_one_hot                  # 3，模型中不要直接把 0/1/2 当连续数
]

球是近似球对称刚体，第一版策略观测可以不输入 ball_quat，但原始数据必须保留。角速度是否输入应做消融：盘带方向控制通常需要线速度，球 spin 对低速控球的增益需要实测。

4.3 目标状态切片

不能只给“目标球位置”而不约束机器人。建议分两类目标：

  • 盘带目标：目标球局部位置、目标球速度、mode；机器人姿态由技能先验和稳定性约束保持。
  • 踢球目标：目标球速度向量或方向+速度、mode；附带接触后稳定目标，避免策略只追求球速而摔倒。
如果目标只包含最终球状态，多个动作序列都可能满足目标，且有些是跌倒式踢球。训练目标和评估必须同时包含机器人存活/稳定性。

5. 统一足球轨迹契约

5.1 推荐容器

沿用 UFO 的 dict[motion_key, record] pkl，每个 record 在标准机器人字段上增加 soccer 字段。建议 schema 名称：

schema_version: ufo_piplus_soccer_v1
robot_config: configs/robots/piplus_h0w.yaml
source_schema: piplus_soccer_motion_v3
ball:
  radius_m: 0.07
  mass_kg: 0.20
  quat_order: wxyz | xyzw   # adapter 输出必须固定并写清
  state_frame: env_local_world
command:
  layout: [ball_x_b, ball_y_b, target_vel_x_b, target_vel_y_b,
           target_ball_pos_x_b, target_ball_pos_y_b, mode]

5.2 NPZ → UFO soccer adapter 的职责

  1. 读取 v3 NPZ，拒绝 object pickle 和缺失关键字段。
  2. 根据 joint_names 重排到 H0W 的 22 关节顺序；不允许仅按列数猜测。
  3. 统一 root/ball 四元数顺序，验证单位范数。
  4. 检查所有时序字段共享相同 T，且无 NaN/Inf。
  5. 将 Isaac 环境 origin 去除后的 world frame 定义写入 metadata。
  6. 生成/验证 pose_aa [T,27,3]；若源 NPZ 已有 body state，优先从其构造，不能伪造。
  7. 保留 action。若采集的 actions 是归一化策略 action，必须记录其 scale 和含义；不要把 joint position 当作 action。
  8. 分别输出完整序列和接近 10 秒训练 clips，并生成 SHA-256、数量、总帧数、fps 分布。
关键缺口：标准 UFO 动作文件主要保存状态，现有足球采集器还保存 policy action。要学习联合状态转移，adapter 与训练 buffer 必须明确使用真正施加的 a_t；只保存 q_t 和 q_(t+1) 不足以监督 action-conditioned transition。

6. 保留本体能力：无球轨迹兼容方案

6.1 推荐方案：inactive object + mask

对现有 H0W LaFAN 轨迹增加统一 soccer 字段，但标记为无球：

object_active = 0
ball_pos_w = root_pos_at_clip_start + [R*cos(theta), R*sin(theta), 0.07]
ball_lin_vel_w = 0
ball_ang_vel_w = 0
foot_ball_contact = 0
command = 0
  • R 建议在安全范围随机采样，例如 2.5–4.0 m；theta 每 clip 随机，避免固定方向偏置。
  • 球位置固定在 world frame，而不是每帧跟随机器人。后者会产生不可能的无作用力跟随运动。
  • 模型输入保留 object_active；对象重建、对象转移、足球目标和接触 loss 对 inactive 样本全部 mask。
  • 机器人状态、动作和原 BFM loss 正常计算，因此旧动作继续维持走、跑、跳、转向等本体能力。

6.2 不推荐方案：未标记的远处固定球

如果只是追加球位置/速度且没有 mask，模型会得到大量“球不遵守物理、永远静止”的样本。其数量通常远多于足球轨迹，会压制对象动力学学习。这个方法只能作为非常短期的 schema smoke，不能作为正式训练数据。

6.3 数据混合

第一轮必须保留独立 source 权重，而不是把所有 clips 合并后均匀采样。建议至少区分：

  • locomotion_no_ball：原 H0W LaFAN，object inactive。
  • dribble_ball：盘带/接球/推球。
  • kick_ball：首次触球前后完整片段。

初始权重不在本文锁死，应通过三组消融确定。最低要求是记录每次训练的实际 source sampling ratio，并分别报告无球和足球指标。

7.1 编码器兼容策略

为了尽量保存已学到的本体表示，第一版推荐：

  1. 保留现有 robot encoder 的输入与参数布局。
  2. 新增轻量 ball encoder 和 command encoder。
  3. 融合层从“原 robot latent + 零对象 latent”初始化为接近旧行为。
  4. 先短期冻结或降低 robot encoder 学习率，仅训练新增分支和融合层；之后再联合微调。
  5. 每个阶段持续跑原 LaFAN tracking/稳定性回归，防止足球 loss 造成灾难性遗忘。

9. 验收门禁与指标

9.1 数据门禁

  • 所有时序 tensor 的 T 完全一致；fps 正数且实际播放时长一致。
  • 22 个 joint_names 与 configs/robots/piplus_h0w.yaml 完全一致。
  • 四元数单位范数；root 与 ball 的 quaternion order 有显式 metadata。
  • 球位置/速度 world↔body 变换可逆，误差在浮点容差内。
  • action 含义明确且与训练环境 action scale 一致。
  • 轨迹 MP4 中足球接触帧与 foot_ball_contact 对齐。

9.2 环境门禁

  • 单环境 deterministic replay：记录状态写回模拟器后，机器人和球位置误差可控。
  • 多环境 reset 后球不串环境，不与地面穿透，不在初始帧爆炸。
  • 观测、reward、action、next state 全部 finite。
  • 禁用 DR 时重复 seed 可复现；启用 DR 时球质量/摩擦范围被记录。

10. 已决策、待决策与主要风险

10.1 已决策

  • 足球训练主型号为 H0W，不以 H1W 直接代替。
  • 优先复用 piplus_soccer_motion_v3 采集器。
  • 对象状态采用局部不变特征进入模型，world state 保留用于回放。
  • 无球轨迹使用 object_active mask。
  • 盘带与踢球先分开训练和验收。

10.2 实现前必须确认

  • 足球 collector 输出的 actions 是归一化 policy action、PD target offset，还是最终 joint target。
  • source NPZ 的 base_quat_w 和 ball_quat_w 精确顺序。
  • UFO soccer 第一版是否需要 ball angular velocity 进入策略观测。
  • 目标状态是直接扩展现有 max_local_self，还是创建独立 object-goal 字段。
  • 在线训练的专家轨迹权重与 LaFAN 权重如何做第一轮消融。
